1. Purpose

This audit records verified findings from the existing repository before implementation of the Direct Runner Marketplace.

The purpose is to preserve working capabilities, identify missing contracts, prevent architectural drift, and avoid unnecessary changes to Core, historical migrations, and released functionality.

This document is an audit record. It does not authorize feature implementation or deletion.

2. Current Product Baseline

The approved direction is Direct Runner Marketplace:

1. Customers create service requests.
2. Eligible runners submit quotations.
3. Customers select one quotation.
4. The Marketplace Engine coordinates selection.
5. Core owns generic TASK identity, assignment, and lifecycle.
6. Business Modules own service-specific data and execution.
7. Approved runners may receive public profiles with unique shareable URLs.
8. Profile-origin requests use the same quotation workflow as marketplace-origin requests.

Historical release records must remain intact. The former v0.3.2 scope and former Pick & Drop Business Workflow MVP scope are cancelled. Their code is not automatically obsolete.

3. Audit Findings

3.1 Core TASK Model

Classification: REUSE

Evidence:

- "backend/app/Models/CoreTask.php"
- "backend/database/migrations/2026_10_15_000001_create_core_tasks_table.php"

Verified capabilities:

- UUID-based generic task identity.
- Module and task type identifiers.
- Source type and source ID.
- Generic task status.
- Assignment and lifecycle timestamps.
- Unique source identity across "module_key", "task_type", and "source_id".

Conclusion:

Core TASK is a reusable foundation. Marketplace must not create a competing generic task lifecycle.

3.2 Core TASK Registry

Classification: REUSE — CONTRACT REVIEW REQUIRED

Evidence:

- "backend/app/Services/CoreTaskRegistryService.php"
- "backend/tests/Feature/Core/CoreTaskRegistrationServiceTest.php"
- "modules/PickAndDrop/Config/module.php"

Verified capabilities:

- Validates module and task type metadata.
- Rejects unsupported or disabled task types.
- Registers tasks using a stable source identity.
- Uses "firstOrCreate" inside a database transaction.

Open questions:

- How should Marketplace requests map to Core TASK records?
- Which component owns task registration after quotation acceptance?
- How should concurrent registration and retry failures be handled?
- How should an existing Core TASK be reconciled with a failed or repeated Marketplace operation?

No Core changes should be proposed until these contracts are defined.

3.3 Core TASK Assignment

Classification: REUSE — MARKETPLACE INTEGRATION REQUIRED

Evidence:

- "backend/app/Services/CoreTaskAssignmentService.php"
- "backend/tests/Feature/Core/CoreTaskAssignmentServiceTest.php"

Verified capabilities:

- Uses a database transaction and row locking.
- Requires an active account.
- Requires approved runner status.
- Requires an open, unassigned TASK.
- Rejects inconsistent assignment fields.

Gap:

These guarantees do not by themselves prove atomic quotation acceptance. Marketplace must coordinate quotation selection, winning-runner assignment, and closure of competing quotations without partial results.

3.5 Runner Approval and Eligibility

Classification: KEEP — EXTEND THROUGH APPROVED CONTRACTS

Evidence:

- "backend/app/Services/RunnerStatusService.php"
- "backend/app/Models/Account.php"
- "backend/routes/api.php"
- "backend/tests/Feature/Core/RunnerStatusServiceTest.php"
- "backend/tests/Feature/Core/RunnerStatusSecurityApiTest.php"

Existing runner statuses include:

- "NOT_RUNNER"
- "PENDING"
- "APPROVED"
- "REJECTED"
- "SUSPENDED"

The existing service supports application, approval, rejection, suspension, and restoration, with authorization checks and audit records.

Gap:

Marketplace must evaluate current eligibility at quotation submission and acceptance. Public profile URLs must never bypass current eligibility.

The behavior of existing assignments when a runner becomes suspended requires explicit design.

3.6 Pick & Drop Request and Internal TASK

Classification: REUSE AS A CANDIDATE BUSINESS MODULE — INTEGRATION GAP CONFIRMED

Evidence:

- "modules/PickAndDrop/Http/Controllers/PickAndDropRequestController.php"
- "modules/PickAndDrop/Models/PickAndDropRequest.php"
- "modules/PickAndDrop/Models/PickAndDropTask.php"
- "modules/PickAndDrop/Routes/api.php"
- "backend/database/migrations/2026_10_09_000001_create_pick_and_drop_requests_table.php"
- "backend/database/migrations/2026_10_09_000002_create_pick_and_drop_tasks_table.php"
- "backend/tests/Feature/Modules/PickAndDrop/PickAndDropRequestTest.php"

Verified behavior:

- An authenticated customer can create a Pick & Drop request.
- The controller creates a corresponding internal Pick & Drop TASK in the same database transaction.
- The internal TASK has its own status.
- The internal TASK's "request_id" is unique, enforcing at most one internal TASK per request.
- Existing tests verify request validation, authentication, snapshots, and internal TASK creation.

Confirmed gap:

The inspected request-creation method does not call "CoreTaskRegistryService" to register a generic Core TASK.

Therefore, the existing request-creation test does not prove that a created Pick & Drop request has a corresponding Core TASK.

Required design decision:

Define the mapping among:

- Business Module request.
- Marketplace service request.
- Runner quotation.
- Core TASK.

Do not assume that all four records are identical or that every conceptual entity requires a separate table.

3.8 Public Runner Profile

Classification: NOT FOUND IN INSPECTED ACCOUNT MODEL AND ROUTES

Evidence:

- "backend/app/Models/Account.php"
- "backend/routes/api.php"

The Account model includes general account information and a profile-picture field. The inspected code does not establish a dedicated public runner profile contract or unique shareable profile URL.

Required design decisions:

- Approved public fields.
- Stable public URL identifier.
- Profile visibility and eligibility rules.
- Targeted request initiation.
- Privacy and profile enumeration protections.
- Attribution and minimum analytics.
- Behavior when a runner becomes unavailable.

The public profile must not expose private account, credential, or security information.

3.9 Identity and SIDCORE

Classification: KEEP CURRENT ACCOUNT AND SESSION BOUNDARIES; INTEGRATION UNVERIFIED

The inspected backend currently uses its own Account and Session models and authentication middleware.

The SIDCORE integration contract has not been verified in this audit.

Before any identity migration or replacement, establish:

- Identity ownership.
- Authentication delegation.
- Session validation and revocation.
- Role and authorization mapping.
- Account lifecycle compatibility.
- Module reference compatibility.
- Migration and regression strategy.

Do not replace the existing identity foundation based on an assumed integration contract.

3.10 Database Migration History

Classification: KEEP HISTORICAL MIGRATIONS

Evidence includes the existing Core TASK and Pick & Drop migrations.

Rules:

- Do not rewrite previously applied migrations.
- Introduce new migrations for approved schema changes.
- Review foreign keys, unique constraints, indexes, and transaction boundaries before designing new tables.
- Preserve the existing module/Core ownership boundary.
- Do not create tables merely because a conceptual architecture lists an entity.

5. Confirmed Risks

1. A module request can exist without a corresponding Core TASK registration.
2. Marketplace quotation acceptance is not yet implemented in the inspected routes.
3. Core assignment safeguards do not alone guarantee atomic quotation selection.
4. A public runner profile could expose private data if implemented by directly serializing Account.
5. Runner eligibility may change after a profile URL has been shared.
6. Identity replacement without a verified SIDCORE contract could break authentication and session guarantees.
7. An unverified CI result could lead to incorrect claims about the current baseline.

8. Audit Conclusion

The existing repository contains reusable Core task, assignment, lifecycle, account security, and runner approval foundations.

The main confirmed functional gaps are the absence of a verified Marketplace request-and-quotation implementation, the absence of a dedicated public runner profile implementation, and the missing Core TASK registration in the inspected Pick & Drop request-creation flow.

The next phase is to complete Batch 0 evidence and then lock the detailed architecture and API/state contracts. Implementation must follow those approved contracts rather than introducing features one endpoint at a time.
